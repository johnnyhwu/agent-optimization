我們每天在跑的，其實是同一個迴圈

Langfuse 沒有不好，它到今天都還是我們 trace 的資料骨幹 —— span 的 input / output / token 都還是從它讀。 缺的是它沒有、而且我們也改不了它 source code 去補的那一段：錯誤定位的分析引擎、疊在 span 上的自訂資訊、以及 skill 的自動優化。

斷點 1：每個 run 的 config，設完就消失

過去
  • 本地起好 agent server，再去設一次 config，跑完 —— 設定就散了
  • 下次想重現同一個 run，只能憑印象再填一次
  • 兩次分數不一樣，是 skill 變了還是 endpoint / model / timeout 變了？說不清楚
Skill Studio
  • 一個 run 記下觸發它的完整設定：endpoints、models、timeout、concurrency
  • 空白欄位在啟動當下就解析成環境的實際值 —— run 是一份完整紀錄，不是對環境的 delta
  • run history 每一列都點得開那份唯讀設定
金鑰只進不出：填得進去，但任何 API 都讀不回來。

斷點 2：答錯了，還要自己翻 trace 找錯在哪

過去
  • 判錯只告訴你「這題錯了」，不告訴你「錯在第幾步」
  • 一天查十題、每題十幾個 span，逐個點開來看
Skill Studio
  • 把理想推理流程的白話描述和實際 trace 一起交給 LLM，問：兩者在哪裡分岔
  • UI 直接跳到最可疑的 span，附上 input / output / token
  • 診斷只算一次就落庫，之後打開是讀資料庫，不重燒 token
給線索，不給判決。嫌疑可以有好幾個、confidence 只有 high / med / low 三檔、 還留了一個 caveat 欄位可以說「這題根本不該歸給單一 span」—— 因為「錯誤可歸因到單一 span」這個假設，本來就常常不成立。

斷點 3：想到怎麼改 skill，卻沒有便宜的方法驗證

過去
  • 唯一的路：改 eval set → 跑一整輪 → 自己用眼睛看結果對不對
  • Langfuse 上只測得了單次 LLM call，測不了一整串 tool calling
  • 於是在 terminal 和 Langfuse 之間來回切，非常麻煩
Skill Studio · Playground
  • 一題、一份可編輯的 skill 副本、一個按鈕：跑完整 trajectory 並自動判分
  • 從錯題一鍵「Try this in the playground」，題目與兩個 ground truth 一起帶過去
  • 送出前比對 skill 版本，基準變了會先問你要重載還是照送
平台不保證 agent 真的吃了你的 override —— UI 直說這件事，而不是假裝有檢查。 證據是那段文字會出現在第一個 span 的 system message。（Optimize 會在花掉一小時前實際驗證，見後面。）

斷點 4：順手想到的好題目，很難留下來

過去
  • 測試中想到的題目，往往正是現有 eval set 沒有的那種
  • 要留下來得手抄回上傳檔，還要自己補一段 thinking process
  • 於是大多數就沒留
Skill Studio · Shortlist
  • 任何一題一鍵進 shortlist，存在瀏覽器裡，backend 重啟也還在
  • Draft from trace：LLM 讀 trace，把 agent 實際做了什麼寫成 thinking process 草稿，人只要改
  • 直接開成新的 eval set；可以勾選既有 set 的題目一起複製進來
預填的 expected answer 標記為 unverified —— 照單全收等於斷言「agent 現在已經是對的」， 那題就會永遠通過，永遠抓不到答案變壞。

然後是最大的一個：迴圈本身太慢

過去
  • 接到新 topic、讀完 domain knowledge 之後，從 0% 爬到 90% 以上：短則 3 天，長則 1～2 週
  • 中間就是人一輪一輪手動改 skill、重跑、看結果
  • 而且說實話 —— 沒有人喜歡調 prompt
Skill Studio · Optimize
  • 像訓練模型一樣訓練一份 skill：epoch / step / learning rate / validation gate
  • 兩種模式：isolated 練 skill 的 body，routing 練 skill 的 description
  • 逐 step 的圖表與 diff：每一步量到什麼、analyst 看到哪些失敗、對 skill 做了什麼
  • 產出是一包 zip，人工放回 agent server
演算法就是後面第三部分要拆的 SkillOpt。

系統全貌：Langfuse 擁有 trace，我們擁有它表達不了的東西

七個 seam 預設全部是 fake，所以這整套在一台只有 Docker 的機器上就能完整跑起來， 也可以一次只把一個真實服務接上來。

別的 team 要接上來，只需要做兩件事

POST {chat endpoint}   一般的 OpenAI chat completions；平台專屬的欄位全部收在一個 key 底下
{
  "messages": [...],
  "skill_studio": {
    "trace_data": { "trace_id": "…" },  ← 請用它當 Langfuse 的 trace id（必要）
    "timeout_s": 120,                   ← 這一次呼叫的預算，取代 server 自己寫死的上限
    "skills": { "billing/SKILL.md": "…" } ← 只對這一次呼叫生效的完整檔案集（選用）
  }
}

GET  {skills endpoint}  → {"skills": {相對路徑: 全文}, "version": "…"}（選用）
                      沒有它，evaluation 照跑；playground、skill 覆蓋率警告與優化功能沒有

correlation id 是整個設計的樞紐

呼叫前我們產生一個 id 放進 metadata，agent server 必須拿它當 Langfuse trace id。 沒有它，平台找不到自己剛剛造成的那條 trace，錯誤定位整個不能運作。 這是唯一一件必須在本系統之外改的事。

skills 是「替換」不是「patch」

只有替換才能表達「刪掉一個檔案」。所以 {} 和「沒給這個 key」 是兩種不同的請求 —— 前者的意思是「完全不帶任何 skill 回答這題」。
完整契約寫在 backend/docs/agent-server-api.md，app 裡的 Documentation 也讀得到。

Part 3

SkillOpt：把 skill 文件
當成可訓練的權重

模型完全不動 —— 所有的「學習」都發生在一份文字檔裡。
論文：arXiv:2605.23904（Microsoft）　·　 我們的實作 vendored 自 microsoft/SkillOpt，只有兩件事換成自己的： 打我們的 agent 取得回答、用我們的 LLM judge 評分。

為什麼不是「讓模型自己反思、自己改 prompt」

常見做法
  • 模型針對上一次的失敗反思，當場改寫 prompt / 技能文件
  • Dynamic Cheatsheet、Agentic Context Engineering 這類 test-time 的情境整理方法，走的都是這條路
三個實務問題
  • 對最近一次失敗過擬合 —— 一次網路延遲、一個措辭奇怪的輸入，都會被當成規律
  • 補丁越塞越肥，文件不斷膨脹
  • 悄悄抹掉先前學到的教訓 —— 發生在純文字上的災難性遺忘
SkillOpt 的回答
不繼續打補丁，而是把整個問題重新框定：
  • 技能文件不是「任人手動修改的檔案」，而是深度學習優化器眼中的一個權重張量
  • 外部的、有版本紀錄的、可訓練的狀態
  • 用受控且有界的步驟更新
  • 通過驗證才保留，沒幫助就回滾
目標模型本身一個參數都沒有改變。

全場的地圖：一張深度學習的對照表

深度學習SkillOpt 的文字空間對應它防的是什麼
參數 W技能文件 best_skill.md300～2,000 token 的一份 Markdown

下面每一個機制存在的理由，都是為了讓左邊那一欄，真的能在文字空間裡運作起來。

兩個模型，各司其職

目標模型 M —— 實際做事的那一方

回答問題、呼叫工具、寫程式。權重與原生 system prompt 全程凍結。 唯一會變的，是被塞進它工作區、或附加在前面的那份 skill。

優化器模型 O —— 完全不碰任務

通常是更強的前沿模型，只在離線訓練階段運作。 讀目標模型的軌跡與分數，然後提出具體的修改：加這條規則、刪那句過時指令、換掉這段模糊措辭。
分開的後果：訓練一結束，優化器那一側的 API 花費就整個消失。 上線的只有凍結的模型，加一份小小的文字檔 —— 部署成本為零。

一個 step，就是這五格

接下來五頁都是同一張圖，只是輪流把其中一格點亮。 整段可以用一句話概括：先收證據，再動手，然後必須通過一場它沒看過的考試才算數。

1　Rollout：動手之前，先收證據

為什麼是一批 40，而不是逐題反應
  • 只對一條失敗軌跡反應，會對那次失敗的特定雜訊過擬合 —— 一次網路延遲、一個措辭特別奇怪的輸入
  • 40 個樣本才有足夠的統計份量，分辨「系統性的弱點」與「單一的偶發狀況」
為什麼要分成兩個池
  • 失敗池：找可以糾正的修復 —— 什麼壞掉了、怎麼補
  • 成功池：找強化 —— 那些已經在發揮作用、但還沒被寫進文件的好習慣。沒記下來，下次未必還能靠運氣重現

2　以 MapReduce 的方式，並行診斷

為什麼 minibatch 大小是 8
  • 是 1：重現我們剛剛才避開的單軌過擬合
  • 是一整池（二十幾條）：超出有用的上下文範圍，還會招致 lost-in-the-middle
  • 是 8：小到留在上下文限制內，大到足以逼模型「橫向比較」，找出跨任務共同出現的失敗模式
分析師的合約
  • analyst_error.md 讀 8 個失敗軌跡 + 目前的技能文件 → 回傳共同失敗模式 + 一份 patch
  • analyst_success.md 做對稱的事，並對已經涵蓋的內容保持保守
  • patch 是原子操作：append / insert_after / replace / delete，每一項都精確定位在文件中的某個目標字串

3　合併，但不失去脈絡

池內：樹狀合併（tree reduce）
  • 提案超過 8 份就每批最多 8 份兩兩合併，直到每個池只剩一份統一的清單
  • 重複的建議收斂成措辭最通用的一版，並附上 support_count —— 有幾個獨立的分析師提出了等價建議
  • 想改同一個位置、但方式互不相容的提案，在這一步就解決掉，不留到之後衝突
跨池：一條毫不含糊的規則

修復失敗，永遠優先

如果成功池的修改與失敗池的修改鎖定同一個位置， 失敗池的版本保留，沒有例外；只有不衝突的成功面修改才活得到下一階段。
修好壞掉的東西，優先級嚴格高於強化已經運作良好的東西。

4　文字版的學習率：編輯預算

餘弦衰減的預算 L t　4 → 2
  • 一次套用太多修改，就跟梯度下降踩了太大的步伐一樣 —— 文件陷入不穩定，丟失先前累積的教訓
  • 前期文件大部分還空著，大幅度的結構性修改是安全的（探索）
  • 後期文件已經有實質內容，只該讓小幅度的用詞微調通過（鞏固）
誰能擠進這個預算：四個排序準則
  • 能修好幾條軌跡（直接掛在 support_count 上）
  • 是否真的補上一個缺口，而不是重述文件裡已經有的話
  • 是否讀起來像一條普遍適用的規則，而不是寫死某個任務的細節
  • 是否具體可操作，而不是空泛的建議
只有排名前 L t 名的修改，才進得了候選技能。

5　真正做決定的，是守門員

資料隔離 + 嚴格的接受規則
  • 優化器只看得到訓練集 D_tr 的軌跡，完全看不到 D_sel
  • 候選技能必須在 D_sel 上獨立打分，而且嚴格大於目前的分數 —— 平手不算
  • 這條門檻堵住的，正是一連串各自看起來都合理、加起來卻只是增加雜訊與膨脹的修改
被拒絕的修改不會浪費
  • 連同它想修的失敗模式、掉了幾分，一起記進被拒修改緩衝區
  • 下一個步驟的分析師與排序器會讀到：「這個我們試過，它傷了驗證分數 —— 別再提」
工程保險：優化器偶爾會幻覺出一個文件裡根本不存在的目標字串。 那一項會被標成 skip 記進 edit_apply_report.json， 同批其他修改照常套用 —— 不讓整條管線崩潰。

每個 epoch 結束時的宏觀調控

慢速更新 —— 受保護的 epoch 層級記憶
  • 抽 20 題，讓上個 epoch 的舊 skill 與這個 epoch 的新 skill 跑同一份固定考卷：受控的 A/B，不是比原始分數
  • 分成進步 / 退步 / 持續失敗 / 穩定成功；退步最重要 —— 它說明最近這些各自都通過驗證的修改，加起來卻讓某些東西更糟
  • 結論寫進 <!-- SLOW_UPDATE_START --> 標記的受保護區塊，一般 step 碰不到它 —— 這就是動量
  • 即使是它，也一樣要過 D_sel 守門，沒幫助就回滾
元技能 —— 教優化器學會優化
  • 優化器寫給自己的筆記：在這個領域裡，哪類修改容易過、哪類容易被拒
  • 只加在優化器下個 epoch 的 system prompt 前面，目標模型永遠看不到
  • 所以部署出去的 skill 一個 token 都不會變胖
我們的狀態：這兩項已經接線，但預設關閉。

優化器一定要前沿等級嗎

把「教練」降級成跟目標模型同一個（小得多的）模型 —— 自己優化自己 —— 有界更新加驗證守門，仍能拿回 56 – 74% 的收益。（表 5）
守門挑的是泛化，不是過擬合

症狀：照原演算法跑，routing run 的分數會一直動、從來不收斂。
三個論證
  • 編輯互斥，merge 救不了。兩個 minibatch 各自 replace 同一行， 本質上互斥；而 merge 拿到的是編輯、不是背後的題目 —— 能決定的證據在上一階段就被丟掉了。 → 整批只做一次 analyst 呼叫，把選擇留在有證據的地方。
  • 失敗與成功是同一個決策邊界的兩面。分開問，失敗分析師會提收窄（看不見收窄弄壞了什麼）、 成功分析師會提放寬（看不見誤觸的那些）—— 這就是一台震盪產生器。 → 一起送，當成一個受約束的問題：涵蓋這些、排除那些。
  • 軌跡對 routing 不構成證據。路由決策發生在 agent 動作之前，完整觀測只有 (題目, 被標記的 skill, agent 實際開啟的 skill)。工具目錄、對話、答案全都付了錢卻無法影響編輯。 → 一整個訓練批次塞得進一個 prompt，比舊的八條軌跡還短 —— 前兩點因此才付得起。
isolated 完全沒有動，仍然是論文的演算法。 偏離的只有 routing，而且是被真實的震盪逼出來的。順帶一提：routing 不送 gold answer，答案外洩的面在這條路上直接消失。

正在探索的下一步

一、同樣的效果，更低的訓練成本
一次十幾小時、燒掉不少 token，最後被接受的修改卻只有一兩次 —— 效率還有很大空間。
  • SkillOpt-Lite　2607.03451
    把 skill 優化形式化成 zeroth-order optimization，砍到「每個元件都有理由」的最小管線； LiveMath 在 GPT-5.5 +8.8、GPT-5.4-nano +25.4，比完整 SkillOpt 更快也更好
  • Naive Prompt Optimization (NPO)　2608.27266
    單一 lineage、teacher 直接讀最近幾版 prompt 與 rollout 寫下一版； 用更少的 rollout 打平甚至贏過 GEPA，質疑候選池與 beam search 是否必要
相鄰方向（不是同一題，但會影響我們怎麼餵它）：
Skill Self-Play 2607.22529 —— proposer / solver / skill controller 共演化，處理「任務多樣性 vs 驗證可靠度」
SkillWiki 2606.16523 —— skill 的來源追溯與治理，回應「domain knowledge 怎麼有憑有據地進到 skill 裡」
二、練出來的 skill 越來越長，怎麼瘦身
SkillOpt 訓練出來的 skill 普遍偏長，而新的 domain knowledge 只會一直加進來。
  • SkillZip　2608.11079
    自我演化的 agent 會不斷把成功程序與失敗修補append 上去， 於是同一條要求被好幾個分支、例子與警告重複陳述，共同的動作序列被複製而不是被重用。 SkillZip 的做法是免評估地壓縮：找出這份 skill 最短的、忠實的結構性解釋
為什麼「免評估」對我們特別有價值：我們最貴的東西就是 rollout。 任何需要再跑一輪驗證才能決定砍哪一段的方法，成本都會疊在已經十幾個小時的訓練上面。

三句話收尾

01迴圈上的每一個斷點，都值得補。
config 留不住、trace 要人翻、假設沒法便宜驗證、好題目留不下來 —— 每一個單獨看都很小，加起來就是開發速度。
02skill 可以當成權重來訓練。
成批的證據取代單一軼事、有界的步伐取代不受約束的重寫、 真正盲測的驗證切分取代「這個改動看起來有幫助」。模型一個參數都不用動。
03optimizer 不取代人，人做最後一哩路。
它把 3 天～2 週壓成一個晚上，然後把一份已經通過驗證的 skill 交到你手上 —— 剩下那 10%、需要台積內部 domain knowledge 的部分，還是人的工作。
