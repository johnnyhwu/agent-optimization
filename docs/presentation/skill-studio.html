We run the same loop every day

Nothing is wrong with Langfuse. It is still the backbone our traces live in — span input / output / tokens are read from it to this day. What's missing is the part it doesn't have and we can't add to its source code: the error-localization engine, per-span information of our own laid over the trace, and automatic skill optimization.

Break 1: the run config is gone when the run ends

BEFORE
  • Start the agent server locally, configure once, run — and the settings scatter
  • Want to reproduce that run tomorrow? Type it in again from memory
  • Two runs disagree: was it the skill, or the endpoint / model / timeout? No way to say
SKILL STUDIO
  • A run records the exact settings it was triggered with: endpoints, models, timeouts, concurrency
  • Blank fields are resolved to the environment's values at start time — a run is a complete record, not a delta against an environment that may since have changed
  • Every row in the run history opens that read-only config
Credentials go in and never come out: you can type a key, no API reads one back.

Break 2: you still have to read the trace yourself

BEFORE
  • A verdict tells you that the question failed, not where it went off the rails
  • Ten questions a day, a dozen spans each, opened one at a time
SKILL STUDIO
  • Hand an LLM the developer's plain-language description of how the question should have been answered and the trace of what actually happened — ask where the two diverge
  • The UI jumps straight to the top suspect span, with its input, output and token counts
  • Generated once and stored; opening it later reads the database, not the model
A clue, not a verdict. Several suspects are allowed, confidence is high / med / low rather than a fake percentage, and a caveat field lets the model say "this isn't attributable to one span at all" — because that assumption is often wrong.

Break 3: no cheap way to test the fix you just thought of

BEFORE
  • The only route: edit the eval set, run the whole thing, read the answers yourself
  • Langfuse tests a single LLM call — not a chain of tool calls
  • So you live between the terminal and Langfuse, switching back and forth
SKILL STUDIO · PLAYGROUND
  • One question, an editable copy of the skill files, one button — full trajectory, judged automatically
  • From a failed question, "Try this in the playground" carries the question and both ground-truth fields over
  • Before each send it re-reads the agent's version: if the skill moved underneath you, it asks first
The platform does not verify that the agent honoured your override — the UI says so rather than implying a check that doesn't exist. The evidence is that the injected text shows up in the trace's first span. (An optimization run does check, before it spends an hour.)

Break 4: the good question you just thought of gets lost

BEFORE
  • A question asked while testing is usually one the eval set doesn't have — that's why it got asked
  • Keeping it means copying it back into the upload file and writing a reasoning description by hand
  • So most of them are never kept
SKILL STUDIO · SHORTLIST
  • One click puts a question on the shortlist — it lives in the browser and survives a backend restart
  • Draft from trace: an LLM reads the trace and writes the reasoning process as a first draft; you only edit
  • Turn the shortlist into a new eval set, optionally copying questions from existing sets in
The prefilled expected answer is marked unverified — kept as-is, that question asserts the agent is already right, so it will always pass and can never catch the answer going bad.

And the big one: the loop itself is slow

BEFORE
  • A new topic, once the domain knowledge is understood: 3 days at best, 1–2 weeks at worst to climb from 0% past 90%
  • All of it is a person editing the skill, re-running, reading results, round after round
  • And frankly — nobody enjoys tuning prompts
SKILL STUDIO · OPTIMIZE
  • Train a skill the way you would train a model: epochs, steps, a learning rate, a validation gate
  • Two modes: isolated trains the skill body, routing trains the skill description
  • A chart per step, plus what that step measured and a side-by-side diff of what it did to the skill
  • The output is a zip you put back on the agent server yourself
The algorithm is SkillOpt — that's Part 3.

The correlation id is the linchpin

We generate an id before the call and pass it in the metadata; your server must use it as its Langfuse trace id. Without it the platform cannot find the trace it just caused, and error localization cannot work at all. This is the one change required outside our repo.

skills replaces, it does not patch

Only replacement can express deleting a file. Which is why {} and an absent key are different requests — the first one means "answer with no skills at all".

Where it stands today

BEFORE
3 days – 2 weeks
A person editing the skill, re-running, reading results, round after round, until the pass rate climbs past 90%. The agent developer is tied up for all of it.
NOW (ISOLATED MODE)
overnight
A run takes a dozen hours or so — press it before you leave, read it in the morning. The person's time moves from tuning prompts to reviewing what came out.
IN USE
  • Several BOD and PPD topics, where it measurably cut the time spent tuning skills
  • Runs cancel and resume; a backend restart leaves a run interrupted, not failed — sign in again and press Resume
  • Four early-stop conditions (validation target hit, N steps without a new best, system error rate too high…) so a bad night doesn't burn to the end

The agent developer is not replaced

THE ROLE CHANGES
  • From "the person who tunes prompts" to "the person who reviews a skill and runs the last mile"
  • Where the optimizer lacks TSMC-internal domain knowledge, accuracy simply stalls around 80% — a person closes the rest
  • The difference: they start from a skill that has already passed validation, not from a blank page
So you can't press the button and walk away for good — someone still has to read that diff in the morning.
LIMITS WE KNOW ABOUT, AND WROTE DOWN
  • Skills are never written back to the agent server: the output is a zip, installed by hand
  • Answer hard-coding has three defences: the analyst prompt forbids it, the validation split is held out, and the diff flags verbatim matches
  • Slow update and meta skill are wired up but ship disabled
  • Diagnosis accuracy itself is unmeasured — that's the evidence we need before investing in the next stage
  • Not every error belongs to one span, and an error in a tool or the base model cannot be fixed by editing a skill

PART 3

SkillOpt: treating a skill file
as a trainable weight

The model is never touched — all of the learning happens in one text file.
Paper: arXiv:2605.23904 (Microsoft)　·　 our implementation is vendored from microsoft/SkillOpt, with only two things swapped for ours: calling our agent for an answer, and scoring it with our LLM judge.

Why not just let the model rewrite its own prompt?

THE USUAL APPROACH
  • The model reflects on its most recent failure and rewrites the skill document on the spot
  • Test-time context-curation methods — Dynamic Cheatsheet, Agentic Context Engineering — all work this way
THREE PROBLEMS IN PRACTICE
  • It overfits to whatever error just happened — a network hiccup, one oddly worded input, taken as a pattern
  • The document bloats with one-off patches
  • It quietly erases lessons learned earlier — catastrophic forgetting, in plain text instead of in weights
WHAT SKILLOPT DOES INSTEAD
It stops patching and reframes the problem:
  • The skill file is not a document someone edits by hand — it is what a deep-learning optimizer sees as a weight tensor
  • External, versioned, trainable state
  • Updated in bounded, controlled steps
  • Kept only if it passes validation; rolled back if it doesn't help
Not one parameter of the target model changes.

The map for everything that follows

Every mechanism below exists for one reason: to make the left-hand column actually work in text space.

Two models, cleanly separated

Target model M — the one doing the work

Answers questions, calls tools, writes code. Its weights and its native system prompt stay frozen throughout. The only thing that changes between rounds is the skill file handed to it.

Optimizer model O — never touches the task

Usually a stronger frontier model, and it runs only during offline training. It reads the target's trajectories and scores, then proposes concrete edits: add this heuristic, delete that stale instruction, replace this vague wording.
The consequence of separating them: when training ends, the optimizer's API spend disappears entirely. What ships is the frozen model plus a small text file — deployment cost is zero.

One step is these five stages

The next five slides are this same diagram with one stage lit at a time. The whole thing in one sentence: gather the evidence, then act, then earn it on an exam the optimizer has never seen.

1　Rollout: gather the evidence first

WHY A BATCH OF 40, NOT ONE FAILURE AT A TIME
  • React to one failed trajectory and you overfit to the noise that caused it — a network hiccup, one oddly worded input
  • 40 samples carry enough statistical weight to separate a systematic weakness from a one-off incident
WHY SPLIT INTO TWO POOLS
  • Failure pool — mined for corrective fixes: what broke, and how to patch it
  • Success pool — mined for reinforcement: good habits already working but not yet written into the skill. Unrecorded, they may not reproduce next time

2　Parallel diagnosis, MapReduce-style

WHY THE MINIBATCH IS 8
  • 1 reproduces the single-trajectory overfitting we just avoided
  • A whole pool (~20) blows past the useful context window and invites lost-in-the-middle
  • 8 is small enough to fit and large enough to force the model to compare across trajectories and find failures that recur across tasks
THE ANALYST'S CONTRACT
  • analyst_error.md gets 8 failed trajectories plus the current skill → returns the shared failure pattern and a patch
  • analyst_success.md does the symmetric job, staying conservative about what is already covered
  • A patch is atomic operations — append / insert_after / replace / delete — each anchored to an exact target string in the file

3　Merge, without losing the context

WITHIN A POOL: TREE REDUCE
  • More than 8 proposals? Merge them in batches of at most 8, pairwise, until each pool holds one unified list
  • Duplicates collapse into the most general wording, carrying a support_count — how many independent analysts asked for the equivalent edit
  • Proposals targeting the same location in incompatible ways are resolved here, not left to collide later
ACROSS POOLS: ONE UNAMBIGUOUS RULE

Fixing failures always wins

If a success-pool edit and a failure-pool edit target the same location, the failure-pool version is kept, no exceptions; only non-conflicting success-side edits survive.
Fixing something broken is treated as strictly higher priority than reinforcing something already working.

4　The learning rate, in text: the edit budget

A COSINE-DECAYED BUDGET L t　4 → 2
  • Applying too many edits at once is like taking too large a step in gradient descent — the file destabilizes and loses hard-won lessons
  • Early on the document is mostly empty, so large structural edits are safe and useful (explore)
  • Later it has real content, so only small wording refinements should get through (consolidate)
WHAT GETS INTO THE BUDGET: FOUR CRITERIA
  • How many trajectories it would fix (tied directly to support_count)
  • Whether it fills a real gap rather than restating what the document already says
  • Whether it reads like a generally applicable rule rather than hard-coding one task's details
  • Whether it is concrete and actionable rather than vague advice
Only the top L t edits make it into the candidate skill.

5　The gate is what actually decides

DATA ISOLATION + A STRICT ACCEPTANCE RULE
  • The optimizer only ever sees trajectories from D_tr. It never sees D_sel at all
  • Every candidate is blind-scored on D_sel, and must be strictly greater than the current skill — a tie doesn't count
  • That bar closes off the classic failure: a string of individually plausible edits that together only add noise and bloat
A REJECTED EDIT ISN'T WASTED
  • It is logged with the failure pattern it targeted and how far the score dropped, into a short-lived rejected-edit buffer
  • The next step's analyst and ranking calls read it: "we tried this, it hurt the validation score — don't propose it again"
Engineering insurance: the optimizer occasionally hallucinates a target string that isn't in the file. That edit is marked skip in edit_apply_report.json and the rest of the batch applies as normal — the pipeline never crashes over it.

The macro control loop, once per epoch

SLOW UPDATE — PROTECTED EPOCH-LEVEL MEMORY
  • Draw 20 tasks and re-run both last epoch's skill and this epoch's skill on the same fixed exam: a controlled A/B, not a raw score comparison
  • Sort into improvements / regressions / persistent failures / stable successes. Regressions matter most — they show that edits which each passed their own gate made something worse together
  • The conclusion goes into a protected block fenced by <!-- SLOW_UPDATE_START -->, which ordinary step-level edits may not touch — that is the momentum
  • Even this isn't trusted: it passes the same D_sel gate or gets rolled back
META SKILL — TEACHING THE OPTIMIZER TO OPTIMIZE
  • A document the optimizer writes for itself: which kinds of edits pass in this domain, and which get rejected
  • Prepended to the optimizer's own system prompt next epoch; the target model never sees it
  • So the deployed skill gains not a single token
Where we stand: both are wired up, and both ship disabled.

The symptom: run the paper's algorithm here and the score moves every step and never settles.
THREE ARGUMENTS
  • Edits collide, and merge cannot reconcile them. Two minibatches each replace the same line — mutually exclusive by construction — and merge is handed the edits without the questions behind them. The evidence that would decide it was discarded one stage earlier. → One analyst call over the whole batch, so the choice is made where the evidence is.
  • Failures and successes are two sides of one boundary. Asked separately, the failure analyst proposes a narrowing (blind to what it breaks) and the success analyst proposes a widening (blind to the misfires). That is an oscillation generator. → Send both to one analyst as a single constrained problem: cover these, exclude those.
  • The trajectory is not evidence about routing. The decision happens before the agent acts; the complete observation is (question, skills it was tagged for, skills the agent opened). The tool catalogue, the conversation and the answer are all paid for and cannot inform the edit. → A whole training batch now fits in one prompt, shorter than one of the old eight-trajectory ones — which is what makes the first two affordable.
isolated is untouched and is still the paper's algorithm. Only routing departs — and it was forced there by a real oscillation, not a preference.

What we're exploring next

1 · SAME RESULT, LESS TRAINING COST
A dozen hours and a lot of tokens per run, for one or two accepted edits at the end. There is a great deal of headroom here.
  • SkillOpt-Lite　2607.03451
    Formalizes skill optimization as zeroth-order optimization and cuts it down to a minimal pipeline where every component is justified; LiveMath +8.8 on GPT-5.5 and +25.4 on GPT-5.4-nano, faster than and ahead of full SkillOpt
  • Naive Prompt Optimization (NPO)　2608.27266
    A single lineage: a teacher reads the most recent prompts with their rollouts and writes the next one. Matches or beats GEPA with fewer rollouts, questioning whether candidate pools and beam search are needed at all
Adjacent, not the same question — but they shape what we feed it:
Skill Self-Play 2607.22529 — proposer / solver / skill controller co-evolving, against task diversity vs. verification reliability
SkillWiki 2606.16523 — provenance and governance for skills: how domain knowledge gets in, with its sources attached
2 · TRAINED SKILLS KEEP GETTING LONGER
SkillOpt's output runs long, and new domain knowledge only ever gets added.
  • SkillZip　2608.11079
    Self-evolving agents accumulate skills by appending successful procedures and failure fixes, so over time the same requirement is restated across several branches, examples and warnings, and common action sequences are copied rather than reused. SkillZip compresses without evaluation: it finds the shortest faithful structural explanation of the skill
Why "evaluation-free" matters to us specifically: rollouts are the expensive thing we have. Any method that needs another round of validation to decide what to cut stacks that cost on top of an already twelve-hour training run.

Three sentences to close

01Every break in the loop is worth repairing.
A config that doesn't persist, a trace read by hand, a hunch with no cheap test, a good question that gets lost — each one is small on its own. Together they are your development speed.
02A skill can be trained like a weight.
Batched evidence instead of single anecdotes, bounded steps instead of unconstrained rewrites, a genuinely blind validation split instead of "this edit looks like it helps". Without touching a single model parameter.
03The optimizer doesn't replace people; people run the last mile.
It compresses three days to two weeks into one night, and hands you a skill that has already passed validation. The remaining 10% — the part that needs TSMC-internal domain knowledge — is still a person's job.
