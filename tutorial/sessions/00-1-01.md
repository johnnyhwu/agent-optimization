# 00-1-01　一個請求的一生：討論暫存檔

## 學習地圖與進度

主線：一個請求從瀏覽器到 DB 再回來。整篇用同一個具體請求走到底：**列出我的 eval set**（`GET /api/eval-sets?limit=24`）。

- [x] 站 1　這篇在解決什麼問題：為什麼要先有「整條路」的地圖（小）
- [ ] 站 2　地圖總覽：四個角色（瀏覽器、nginx、後端、DB）各自負責什麼，一句話版（小）
- [ ] 站 3　旅程上半：瀏覽器怎麼拿到頁面、怎麼發出請求（`config.js`、`fetch`、`/api` 前綴）（中）

## repo 查證結果

**有做**。四個角色都能指到檔案：

- 瀏覽器端發請求：`frontend/src/api.js`（`req()` 用 `fetch(BASE + path, …)`；`listEvalSets` 在 `api.js:212`）。`BASE` 來自 `frontend/src/app_config.js`，優先讀 nginx 啟動時產生的 `/config.js`，其次才是 Vite 建置時的變數。
- nginx：`frontend/nginx.conf.template`。靜態檔由 `root /var/www` 提供；`location /api/` 用 `proxy_pass ${API_URL}/;`，結尾的 `/` 會把 `/api` 前綴剝掉；進度串流有另一個 regex location（`proxy_buffering off`）。
- 後端：`backend/app/main.py`（FastAPI app，掛 router、CORS、`/health`）；列表端點是 `backend/app/routers/eval_sets.py:429` 的 `list_eval_sets`，用 `Depends(current_subject)`（`backend/app/auth.py:60`）驗身分、`Depends(get_session)`（`backend/app/db.py`）拿 DB session。
- DB：`backend/app/db.py` 建 async engine + connection pool；`docker-compose.yml` 的 `db` 服務（Postgres），後端以 `DATABASE_URL=…@db:5432/…` 連線。

**做法不同 / 值得一提（一兩句，使用者想深入才展開）**：

- 同源設計（nginx 同時服務靜態檔與 `/api`）是合理取捨：前端不用寫死後端網址、CORS 不會觸發。缺點是 nginx 成為單一入口，timeout 等設定要與後端的長請求一起調（`nginx.conf.template` 註解有寫）。
- 連線池是後端真正的併發上限（`db.py` docstring），屬 02-2-01 的主題，這篇只點到。

## 站 1 內容摘要（成稿材料）

- 一句話：系統不是一個東西，是一條路上的四站；先有整條路的地圖，之後每一章才知道自己在補哪一站。
- 核心論點：出問題時，症狀會告訴你壞在哪一站。以「畫面要列出我的 eval set」為例：
  - 整頁空白、JS 載不下來 -> 站 1～2（瀏覽器拿靜態檔／nginx）
  - 502 / 504 -> nginx 與後端之間
  - 401 -> 後端的身分驗證
  - 200 但清單是空的 -> 後端查詢或 DB 的資料
- 例子：`nginx.conf.template` 的註解記錄了真實情境：後端跑很久，nginx 的 timeout 比較小，使用者好幾分鐘後看到沒有訊息的 504。這是「跨兩站的設定要一起調」的例子。
